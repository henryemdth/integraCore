## Users view: newest-first ordering + realtime refresh + suggestion search

**Analysis summary:** `userService.list()` orders by `full_name ASC` and accepts no search; the socket layer has no users event; the Phase 33 Products suggestion pattern would be duplicated a second time, so it gets extracted into a reusable component. Usernames are UNIQUE on both drivers (exact pick-fill target); `created_at` exists on both.

### Implementation

**1. Ordering (default: newest user on top)** — `userService.list()`: `ORDER BY created_at DESC, id DESC` (Phase 32 pattern; driver-neutral on TEXT/TIMESTAMP). Blast radius: only the Users table and the Sales seller dropdown (harmless).

**2. Realtime refresh** — new `emitUsersChanged()` in `socket/index.ts` emitting `"users:changed"` (payload-less signal, matching the existing emitter style). Called from `authService.register` (creation — the requirement) and `userService.update/activate/deactivate` (edits/role/status keep the dashboard live too; resetPassword changes no list data → skipped). Frontend `SocketContext` listens and invalidates `["users"]` — the same invalidate-only pattern as `product:updated`; it catches the paged list, stats, and the seller dropdown by prefix. No conflicts with the dialogs' own local invalidation. No new SQL → identical on SQLite and Postgres.

**3. Suggestion search, extracted as a reusable component** — new `frontend/src/components/ui/suggestive-input.tsx`: generic `SuggestiveInput<T>` owning the dropdown open state, normalized matching (`normalizeForSearch` over `itemText(item)`), the click-away backdrop, Escape handling, and the search-icon input. Props: `value/onValueChange`, `items`, `itemText`, `itemKey`, `renderItem?`, `onPick`, `placeholder`, `maxSuggestions`. **ProductListPage is refactored onto it (behavior-identical)** so there's exactly one implementation, then **UserListPage** uses it with `full_name + username` matching, rendering name + username, and picking fills the search with the **username** (unique → exactly that user).

**4. Server-side search for users** — `userService.list()` gains a `search` param (`username LIKE %s% OR full_name LIKE %s%`; PG gets ILIKE automatically via the Phase 29 transform), forwarded by `routes/users.ts`; UserListPage wires it into params + query key like Products. Typing filters the table; picking pins it to one user.

**5. Tests + verification** — `userService.test.ts`: ordering test (second-seeded user ranks first via id tiebreak), search test (case-insensitive on username/full_name); socket `vi.mock` factories in `userService.test.ts` and `authService.test.ts` gain `emitUsersChanged`; assert register emits it. Then: backend suite + typechecks; frontend lint/build; en/es parity (+1 key `users.searchPlaceholder`); GUI on the isolated env (newest-first order; type "adm"/"bru" case-insensitively → suggestions; pick → exactly that user; create a second browser-agnostic check of the socket path by verifying `users:changed` invalidation logic via the mocked unit tests + manual API-created user appearing after refetch) with screenshots; MEMORY.md Phase 34.
