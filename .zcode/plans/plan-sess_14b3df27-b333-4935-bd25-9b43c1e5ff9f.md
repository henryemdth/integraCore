## Discounts dashboard: filters + newest-first ordering

**Analysis summary:** `GET /api/discounts` (`listAll()`) takes no params and orders only by `start_date DESC` — so the last-added discount doesn't reliably sit on top (a backdated one sinks; same-second creations are nondeterministic). The page has no filters, ignores the dead deep-link `/discounts?productId=` that Products emits, and the Excel export ignores any filtering. `created_at` exists on both drivers, and discount "status" (Active/Scheduled/Expired/Cancelled) is a *derived* value the page already computes — the same derivation is expressible server-side with `nowString()` params, the exact pattern `getActiveDiscount` already uses on both SQLite and Postgres. The Sales page's filter bar is the reuse template.

### Implementation

**1. Ordering (the reported issue)** — in `discountService`: `listAll()` and `exportHistory()` (Excel must match the dashboard) become `ORDER BY pd.created_at DESC, pd.id DESC` — creation order, newest first, with the id as deterministic tieback for same-second rows. Product-scoped `list()` gets the same ordering for consistency (no UI consumer today, zero risk). Plain `ORDER BY` on `created_at`/`id` is identical on TEXT (SQLite) and TIMESTAMP (Postgres).

**2. Server-side filters (Status + Product)** — new private `buildDiscountFilter(filters)` in `discountService` shared by `listAll` and `exportHistory`:
- `productId` → `pd.product_id = ?`
- `status` whitelist, derived-status semantics mirrored from the client badges, all param-injected (`now = nowString()`): `active` → `status='active' AND start_date <= now AND end_date >= now`; `scheduled` → `status='active' AND start_date > now`; `expired` → `status='active' AND end_date < now`; `cancelled` → `status='cancelled'`. Unknown values apply no condition.
- Routes `GET /api/discounts` and `GET /api/discounts/export` read `product_id` and `status` query params and forward them (also fixes the export-ignores-filters gap).

**3. Frontend filter bar** (`DiscountHistoryPage.tsx`, mirroring `SalesListPage`): CardHeader row with Label + `SearchableSelect` for Product (options from the existing `["products","list-all"]` query, `keywords: [sku]`, allLabel "All products") and Label + plain `Select` for Status (All / Active / Scheduled / Expired / Cancelled, reusing the existing badge i18n keys). Query becomes `["discounts", filterParams]` + `URLSearchParams` + `placeholderData`. The page initializes the product filter from `?productId=` (`useSearchParams`), making the ProductListPage → discount-history deep link work. The Export button passes the current filters like the Sales export does. Row badges, Cancel/Delete mutations (invalidate `["discounts"]` prefix — still matches the keyed query) stay as-is.

**4. i18n** — add only `discounts.allProducts` and `discounts.allStatuses` (en/es, parity-checked); everything else (`discounts.product`, `status`, `active/scheduled/expired/cancelled`, `common.*`) already exists.

**5. Tests + verification** — extend `discountService.test.ts`: ordering (a later-created discount with an earlier start_date must rank first), product filter, and each derived status (seed past/future/cancelled discounts via `create`/`cancel`); unknown status ignored. Then the usual pass: backend suite + `tsc --noEmit` + `typecheck:test`; frontend lint + build; en/es parity; GUI on the isolated env (seed one active, one scheduled, one expired, one cancelled discount → verify newest-first order, both filters, the deep link from Products, export) with screenshots; MEMORY.md Phase 32.
