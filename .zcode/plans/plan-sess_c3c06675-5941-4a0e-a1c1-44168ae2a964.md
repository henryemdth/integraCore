# Plan: Fix discount dates rendering as "day 1" (PostgreSQL timestamp serialization)

## Root cause (confirmed by code reading)

The Discount view renders `formatDate(d.start_date)` / `formatDate(d.end_date)`, and the frontend `formatDate` parses the SQLite TEXT contract: split on `" "`, then `y-m-d`. The backend services return raw rows (`SELECT pd.* …`).

- **SQLite (local dev)**: TIMESTAMP-like columns are TEXT — `"2026-07-07 23:59:59.999"` → parses fine.
- **PostgreSQL (cloud: Render + Neon — where you're seeing the bug)**: `pg` materializes TIMESTAMP columns as **JS `Date` objects**, which JSON-serialize as ISO — `"2026-07-07T23:59:59.999Z"` (with a `T`, not a space). `formatDate` then computes `Number("07T23:59:59.999Z")` = `NaN` → falls back to `d || 1` → **every date renders as the 1st** of its month. Exactly your symptom.

Same root cause breaks, on the cloud only:
- the Active/Scheduled/Expired badges (`d.start_date <= now` string-compare is cross-format: `'T' > ' '`);
- the **inventory Excel export** — `productService.ts:148` calls `d.end_date.slice(0, 10)`, which throws on a `Date` object (export crashes on PG).

Your local dev is SQLite, which is why it looks fine there; the Discount view you're looking at is served by the cloud backend.

## Fix: normalize timestamps at the adapter boundary (plus defensive frontend)

The architecture rule (AGENTS.md) is that the DB adapter is the dialect-conversion layer — it already rewrites `?`→`$N` and `datetime('now')`→`NOW()`. Timestamp *serialization* is part of that same dialect difference, so:

1. **Backend — new pure function** `normalizeRowDates` (in `backend/src/db/postgres-row-normalize.ts`): converts every `Date` instance in a result row to `"YYYY-MM-DD HH:MM:SS.mmm"` using **UTC getters** — mirroring the TEXT contract that `datetime('now')` writes on SQLite and keeping digits identical to what was stored on the UTC-hosted cloud DB. Non-Date values (including `null`) pass through untouched.
2. **Backend — apply in `PostgresAdapter`**: call it in `get()`, `all()`, and the transaction adapter's `get/all`. No changes to services, routes, or frontend logic — discounts, products' `discount_end_date`, sales/notifications `created_at` all come back as the canonical space-format strings again, restoring badge comparisons and fixing the Excel export crash.
3. **Frontend hardening** (`lib/format.ts`): `formatDate` splits on `/[ T]/` instead of `" "` so an ISO string can never silently render as day 1 again; `formatDateTime` gains a small robust local parser for space-format strings instead of relying on `new Date()`'s implementation-defined handling.

## Behavior note (intentional)

Sales/notification timestamps on the **cloud** will display like your SQLite dev does today (both use the same convention), instead of the current cloud-only ISO handling — one consistent display convention across deployments for this single-timezone business.
